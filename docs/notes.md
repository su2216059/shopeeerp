1、put 流程怎么走（hash、定位桶、处理冲突）
根据key计算hashcode值，然后定位桶位置，主要通过位运算，处理冲突，桶位为空直接新建node,桶位置有值,key相同则直接覆盖，桶有值，key不同则遍历桶，链表就尾插在后面，如果是树结构则进行红黑树插入计算，
2、扩容触发条件是什么
hashMap中的元素数量超过阈值，阈值=（容量*负载因子）
3、扩容怎么迁移（rehash/扰动/拆分）
hashMap扩容时元素只有两个结果，原位置/原位置+旧容量，key值根据与运算符判断结果，0则保持原位置，不为0则到原位置+旧容量，链表迁移时会生成两组链表，低位链表、高位链表，根据key判断结果遍历链表分别插入到低位和高位链表后，树结构迁移则是同样判断key值得与运算结果，先把树结构拆分成链表，如果长度小于6则退回成链表结构，反正则在新位置重新构建树结构
4、为什么要红黑树
为了保证查询性能，如果全用链表则可能导致大量相同得hash值在一个链表里，长度越长，时间复杂度则是O(n),引入红黑树可保证时间复杂度为O(log n)
5、树化条件是什么
当链表长度大于8且数组长度>64得时候则进行树化，
6、为什么要有 loadFactor
为了平衡查询与插入性能最大化
7、ArrayList 扩容
因为底层是数组，连续得内存，一旦创建无法修改，当add时，会判断是否大于数组容量，是的话则调用扩容得方法，一般为原数组长度的1.5倍，它会申请新的空间创建数组，然后把旧数据通过内存拷贝到新数组里，丢弃旧数组，交给GC

因为非叶子节点只存索引，叶子节点只存数据，且叶子节点按顺序形成链表，所以适合范围查询

3、回表是什么，怎么避免
回表 = 先用二级索引定位主键，再拿主键去聚簇索引表中查整行数据。
总结
“InnoDB 使用 B+Tree 索引，所有数据都在叶子节点，并通过双向链表串联，因此天然支持高效的范围查询。
覆盖索引是指查询字段都在索引中，可以直接从索引返回结果，避免回表；
回表是指先走二级索引拿主键，再去聚簇索引取整行数据，可以通过设计覆盖索引来避免。”

Day8
1、线程池的核心参数里，你最容易踩的两个坑是什么？
1）使用无界队列（如默认 LinkedBlockingQueue），在高流量下会无限堆积任务导致 OOM；
2）core/max 配置不合理：core 过大浪费 CPU，上下文切换严重；过小又容易频繁排队或扩容抖动。
一般会结合 CPU 核数、任务是 CPU 密集还是 IO 密集来综合配置，而不是固定公式套用。
2、synchronized vs ReentrantLock 的核心区别？
1）实现层面：synchronized 是 JVM 关键字，ReentrantLock 是 JUC 类；
2）灵活性：ReentrantLock 支持 tryLock、可中断、公平锁、Condition，而 synchronized 不支持；
3）使用方式：ReentrantLock 需要手动 unlock，synchronized 自动释放；
4）可读性：简单场景优先 synchronized，复杂并发控制优先 ReentrantLock。
3、什么场景必须用线程池而不是手动 new Thread
以下场景必须用线程池而不是 new Thread：
1）高并发请求（避免线程爆炸与 OOM）；
2）短任务高频执行（避免频繁创建/销毁线程的开销）；
3）需要限流、削峰或异步化的业务场景。
生产环境基本禁止直接 new Thread。
4、你理解的 CompletableFuture 是什么？解决了什么痛点？
CompletableFuture 是 JDK8 提供的可组合的异步编程框架，既能异步执行任务，又能通过 thenApply、thenCombine、allOf 等方式编排多任务协作。
它解决的痛点是：回调地狱 + 同步阻塞 + 多任务协同复杂。
默认使用 ForkJoinPool.commonPool，生产环境我会自定义线程池避免资源争抢。
5、如果线程池队列满了，你会怎么设计拒绝策略？
① 优先级低业务：用 CallerRunsPolicy 或直接丢弃并打告警日志；
② 核心业务：降级 + 限流（返回友好提示或暂时排队）；
③ 异步兜底：把任务投递到 MQ/消息队列，后续补偿处理。

Day 11
1、JVM 内存结构里你最关心哪几块？为什么？
最关心堆、栈、方法区，因为这是程序中一直用到的地方，堆管理新建对象空间啊，栈线程私有数据管理处，方法区管理类信息，公共数据
-----------
我最关注三块：堆、元空间、栈。

堆：承载几乎所有对象，直接决定系统是否 OOM，也是 GC 的主战场；

元空间：存类元数据，项目里大量动态代理/框架容易把它撑爆；

栈：每个线程私有，决定线程能跑多深的方法调用链，栈溢出常见于递归或线程过多。

生产上我主要盯堆 + GC，排障时优先看它。
2、Minor GC 和 Full GC 的核心区别？
Minor GC主要回收新生代数据， Full GC主要回收老年代对象，MinOr GC回收频繁速度快，Full GC回收慢，占内存
------------------
Minor GC 只回收新生代，通常非常频繁、暂停时间短；
Full GC 会同时回收老年代 + 元空间（多数实现），暂停时间长、对业务影响大；
如果频繁触发 Full GC，基本意味着内存泄漏、内存配置不合理或晋升过快
3、常见的 OOM 有哪几种？你见过哪种？
Heap OutOfMemoryError 堆溢出 只见过这种，最常见的，内存使用无限增长，或者导出数据创建了一个大对象
Metaspace OOM 元空间溢出
加载大量类
Direct Memory OOM 
分配 DirectBuffer 太多但没及时释放
Unable to create new native thread
线程太多
GC overhead limit exceeded
垃圾回收工作量太大，一般内存泄漏、堆太小都会引起
---------------
常见 OOM 有四类：
1）Heap OOM：对象太多或内存泄漏（我在导出大数据时遇到过）；
2）Metaspace OOM：加载大量类或动态代理失控；
3）Direct Memory OOM：NIO 直接内存使用过多未释放；
4）Unable to create new native thread：线程创建过多，触达系统限制。

我线上最常见的是 Heap OOM。
4、线上 CPU 飙高，你第一步会怎么排查？
先用top查询占cpu最高的java进程 ，再找到线程，通过把线程id打印成16进制的数字，然后根据jstack命令找到具体代码执行行数，基本可以定位问题

先用 top 找到 CPU 最高的 Java 进程；
再用 top -Hp <pid> 找到占 CPU 最高的线程 ID；
把线程 ID 转成 16 进制，用 jstack <pid> 定位到具体栈帧；
最终确认是哪段代码在“死循环、频繁计算或锁竞争”。
5、如果接口突然变慢，你的排查顺序是什么？
一般先看业务，是否调用其他业务，有无http请求，或者调用其他服务，加打印日志查询执行时间，最后看是否数据库查询速度耗时过慢
----------------
第一层：应用层
看日志、线程池、是否有大量阻塞或远程调用超时；

第二层：数据库
看慢 SQL、EXPLAIN、索引是否失效、连接池是否打满；

第三层：JVM
看 GC 是否频繁、是否有 Full GC 或 STW 抖动。

按“由外到内、由快到慢”的顺序排查。
6、你理解的 GC“安全点（Safepoint）”是什么？
就是JVM可以在一个安全的时刻统一做事情的时刻
--------------
Safepoint（安全点）是 JVM 选定的一些“确定不会改变对象引用关系”的位置，比如方法调用、循环回边、异常抛出等；
当需要 GC、偏向锁撤销、类卸载等全局操作时，JVM 会让所有线程在最近的 Safepoint 挂起，形成 STW；
因此如果代码里有长时间不进入 Safepoint 的计算密集循环，可能会延迟 GC 触发。
